Documento de diseño de la solución

Sistema de gestión para tueste, procesado y venta de café

Cubre inventario multietapa, compras, producción (beneficiado, trillado, tueste, molido), servicios a terceros, clientes, pedidos y ventas — desde el grano cereza hasta la taza empacada con marca propia.

Versión 2.0 Fecha 13 oct 2026 Stack Next.js · Supabase · Vercel Estado Implementado — sitio de pruebas publicado
01

Contexto y objetivo

El negocio combina tres actividades sobre un mismo insumo — el café — con reglas de inventario distintas cada una:

Producción propia. Compra de cereza/pergamino/verde a proveedores, procesado interno y venta bajo marca propia al menudeo y mayoreo.
Servicio a terceros. Tostado, pelado, molido o procesado de café que pertenece al cliente — se cobra por el servicio, no se compra ni se vende el grano.

El sistema debe distinguir siempre estas dos rutas: un lote propio afecta inventario y costos; una orden de servicio afecta solo cuentas por cobrar.

07

Diseño de base de datos

El esquema real difiere bastante del diseño original de este documento (ver versión anterior en el historial) — evolucionó durante la construcción conforme aparecieron reglas de negocio no anticipadas, sobre todo que no todo lo que se compra/vende es café propio (insumos de empaque, reventa de producto terminado). Lo que sigue es un reflejo fiel del esquema en supabase/migrations/ a la fecha de este documento, no una propuesta.

7.1 — Tabla de auditoría (append-only, con retención)

Registra cada INSERT/UPDATE/DELETE sobre tablas críticas vía trigger SECURITY DEFINER. La inmutabilidad frente a la aplicación se logra por privilegios (sin GRANT de update/delete a los roles de API), no por un trigger bloqueador — eso deja espacio para que un job de mantenimiento sí pueda purgar registros vencidos.

create table audit_log (
  id bigint generated always as identity primary key,
  table_name text not null,
  record_id text not null,
  operation text not null check (operation in ('INSERT','UPDATE','DELETE')),
  old_data jsonb,
  new_data jsonb,
  changed_by uuid default auth.uid(),
  changed_at timestamptz not null default now()
);

-- Inmutable de cara a la app: ningún rol de API puede editar/borrar
revoke update, delete on audit_log from anon, authenticated;

-- Retención configurable — purga automática vía pg_cron (incluido en plan Free)
create or replace function fn_purge_audit_log(retencion_dias int default 15)
returns void language sql security definer as $$
  delete from audit_log
  where changed_at < now() - (retencion_dias || ' days')::interval;
$$;

select cron.schedule('purge-audit-log', '0 3 * * *', $$select fn_purge_audit_log(15)$$);

15 días es el punto de partida — súbelo si te interesa poder investigar un ajuste de inventario raro varias semanas después; a esta escala de datos, 90 días no representa un costo de almacenamiento relevante.

7.2 — Inventario de insumos y productos terminados (implementación real)

La versión anterior de este documento proponía un producto_terminado separado con un ledger de movimientos_inventario (stock calculado por sum()). Eso no se implementó así. La necesidad real resultó más simple que distinguir "propio vs. reventa": lo que varía no es el origen del artículo, sino si es algo que se consume (insumo: bolsas, etiquetas) o algo que se vende (producto terminado) — y ambos pueden comprarse a un proveedor igual. De ahí surgió un catálogo único:

create table articulos (
  id uuid primary key default gen_random_uuid(),
  tipo text not null check (tipo in ('insumo','producto_terminado')),
  nombre text not null,
  unidad_medida text not null,       -- "bolsa", "pieza", "kg", etc. — libre, no catálogo aparte
  stock_actual numeric not null default 0,
  precio_venta numeric,              -- solo aplica a producto_terminado
  activo boolean not null default true
);

-- compras: una compra puede generar un lote (café) O sumar stock a un
-- articulo (insumo o producto de reventa) — nunca ambos a la vez
create table compras (
  id uuid primary key default gen_random_uuid(),
  tipo_compra text not null check (tipo_compra in ('lote','insumo','producto_terminado')),
  proveedor_id uuid not null references proveedores(id),
  lote_id uuid references lotes(id),
  articulo_id uuid references articulos(id),
  costo_total numeric,
  creado_por uuid references usuarios(id)
);

stock_actual se mantiene directo (se suma/resta dentro de cada función security invoker — registrar_compra_articulo, empacar_lote, eliminar_empacado, ventas, ajuste manual), no por un ledger de movimientos separado. Se aceptó ese trade-off: menos tablas y queries más simples, a cambio de que el historial de "por qué cambió el stock" vive repartido en varias tablas (compras, empacados, venta_items) en vez de en un solo lugar — hoy es suficiente porque cada una de esas tablas por sí sola responde esa pregunta para su propio caso.

7.3 — Receta de insumos por producto (bill of materials)

Agregado 12-oct-2026, no estaba en el diseño original. Antes, al empacar se podía elegir un insumo opcional a descontar; en la práctica un producto necesita varios (bolsa + etiqueta + sticker), cada uno en cantidad distinta. Se resolvió con una tabla de receta configurable desde el catálogo de artículos, y una tabla de consumo real para poder revertir un empacado eliminado:

create table articulo_insumos (   -- la receta: qué insumos y cuántos necesita un producto
  id uuid primary key default gen_random_uuid(),
  articulo_id uuid not null references articulos(id) on delete cascade,  -- producto_terminado
  insumo_articulo_id uuid not null references articulos(id),            -- insumo
  cantidad_por_unidad numeric not null check (cantidad_por_unidad > 0),
  check (articulo_id <> insumo_articulo_id),
  unique (articulo_id, insumo_articulo_id)
);

create table empacados (          -- un empacado real (sin la columna insumo_articulo_id original)
  id uuid primary key default gen_random_uuid(),
  lote_origen_id uuid not null references lotes(id),
  articulo_id uuid not null references articulos(id),     -- producto_terminado generado
  presentacion_id uuid not null references presentaciones(id),
  unidades numeric not null check (unidades > 0),
  peso_kg numeric not null check (peso_kg > 0),
  usuario_id uuid references usuarios(id)
);

create table empacado_insumos (   -- qué insumos (y cuánto de cada uno) se consumieron en ESTE empacado
  id uuid primary key default gen_random_uuid(),
  empacado_id uuid not null references empacados(id) on delete cascade,
  insumo_articulo_id uuid not null references articulos(id),
  cantidad numeric not null check (cantidad > 0)
);

empacar_lote(lote, articulo, presentación, unidades) ya no recibe un insumo a mano: lee la receta de articulo_insumos, valida en una primera pasada que haya existencia suficiente de todos los insumos antes de descontar nada (todo-o-nada), y solo entonces descuenta cada uno y dejará constancia en empacado_insumos. eliminar_empacado revierte el peso del lote, el stock del producto y todos los insumos consumidos (no solo uno), leyendo esa misma tabla.

13.4 — Prioridad de renovación

  1. Ninguna acción urgente. Nada de lo instalado está fuera de soporte ni tiene una fecha de vencimiento cercana — Node 24 sigue recibiendo seguridad hasta 2028, Postgres 17 hasta 2029.
  2. Mantenimiento de rutina (próximo ciclo): actualizar next, react, @supabase/supabase-js, zod, lucide-react, jspdf, @playwright/test y vitest a sus versiones menores más recientes — son cambios de bajo riesgo.
  3. Evaluar con cuidado: eslint 10.x y framer-motion 14.x (revisar cada changelog antes de subir, son versiones mayores).
  4. Posponer deliberadamente: typescript 7.x, hasta que el ecosistema de plugins confirme soporte — subir primero a 6.x como paso intermedio cuando se decida avanzar.
  5. Vigilar, no actuar todavía: @supabase/ssr (sigue pre-1.0) y @material/web (partes experimentales) — no requieren actualización, pero cualquier bug raro de la UI vale la pena revisarlo contra el changelog de estas dos antes de asumir que es un bug propio.
14

Glosario cafetero

Cereza
Fruto del café recién cosechado, con pulpa y cáscara.
Beneficiado
Proceso que retira la pulpa de la cereza — lavado, honey o natural, según cuánto mucílago se deja.
Pergamino
Grano tras el beneficiado, aún envuelto en su cáscara interna (endocarpio).
Trillado / pelado
Retira el pergamino y deja el grano verde (oro), listo para tostar.
Verde / oro
Grano crudo sin tostar — la unidad de inventario que se compra/vende entre productores.
Tueste
Aplicación de calor según un perfil (curva de tiempo/temperatura) que define sabor y color final.
Merma
Pérdida de peso entre una etapa y la siguiente (ej. el tueste reduce el peso ~15–20%).
Documento vivo — se actualiza conforme avanza el sistema. Próxima revisión: al separar un proyecto Supabase de producción real, o al integrar observabilidad (§10).
